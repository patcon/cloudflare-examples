# Plan: polis-durable-object

A minimal Polis-style conversation running in a Durable Object. Participants add statements and vote agree, disagree or pass. An alarm recomputes the opinion groups, and a live scatter plot of every participant updates over WebSockets. An admin page seeds a conversation from a Polis CSV export.

There's no project or group-chat scope, no moderation and no real auth yet. Each is a later layer (see [Later](#later)).

## Suggested Amendments

None for now.

## Stack

- **Worker:** Hono. It routes requests and checks who the caller is. The DO trusts it, as in `../dembrane-auth-cookie`.
- **Durable Object:** one `Conversation` per conversation ID (binding `CONVERSATION`), using the raw `DurableObject` API with SQLite storage. No PartyServer.
- **Frontend:** React, built with Vite and `@cloudflare/vite-plugin`. The plugin runs the Worker and the DO in workerd during `vite dev`.
- **Client WebSocket:** `partysocket`, a WebSocket that reconnects by itself with backoff.
- **Package manager:** pnpm. This example is standalone, with its own config, `.gitignore` and lockfile.

The layout follows Cloudflare's official [`vite-react-template`](https://github.com/cloudflare/templates/tree/main/vite-react-template): `src/worker/` and `src/react-app/`, split tsconfigs, and SPA asset handling.

## Pages

The React app is a single-page app. `main.tsx` reads `location.pathname`:

| Path | Page |
|---|---|
| `/` | Home: a link or button to a new conversation at a random ID |
| `/:convoId` | Participant |
| `/:convoId/admin` | Admin (no auth, on purpose, for the demo) |

Any conversation ID works. `getByName(convoId)` creates an empty conversation the first time it's used, so there's no separate create step.

## Identity: participant cookie

- The Worker's `/api/*` middleware sets `polis_participant=<random UUID>` if it's missing: `HttpOnly; SameSite=Lax; Path=/; Max-Age=1 year`.
- **The cookie value is a secret.** The Worker derives the public `participantId = first 16 hex chars of SHA-256(cookie)` and passes only that to the DO. Participant IDs are sent to everyone (for the scatter plot), so they must not work as credentials.
- **Why a cookie:** browsers send cookies on the WebSocket upgrade but won't let you set headers on it. It's also the same shape as `dembrane_session_token`. Adding real auth later means changing `participantId` to the Directus user ID.
- **Order on page load:** `GET /api/:convoId/me` first (it sets the cookie and returns `participantId`), then open the socket. Otherwise the first page load could race and create two identities.
- **Cross-origin writes:** requests that change something need `sec-fetch-site: same-origin` or a matching `Origin`, as in `../dembrane-auth-cookie/src/auth.ts`.

## API

| Route | What it does |
|---|---|
| `GET /api/:convoId/me` | `{ participantId }` (and sets the cookie) |
| `GET /api/:convoId/next` | A random statement you haven't voted on, or `null` |
| `POST /api/:convoId/statements` | `{ text }` → the new statement. Trimmed, 1–1,000 characters |
| `POST /api/:convoId/votes` | `{ statementId, vote: -1 \| 0 \| 1 }`. An upsert, so the last vote wins |
| `GET /api/:convoId/ws` | WebSocket upgrade, forwarded to the DO's `fetch()` |
| `POST /api/:convoId/import` | Multipart form with `comments` and `votes` files → `{ statements, participants, votes }` imported |

Votes: 1 = agree, −1 = disagree, 0 = pass. This matches Polis's `votes.csv` (its database flips the signs, but the export flips them back: `server/src/routes/report.ts`).

## Conversation DO

The schema is created in the constructor inside `blockConcurrencyWhile`:

```sql
CREATE TABLE IF NOT EXISTS participants (
  id TEXT PRIMARY KEY,               -- hashed cookie, or 'polis:<voter-id>' for imported participants
  source TEXT NOT NULL,              -- 'local' | 'polis'
  created_at INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS statements (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  author_id TEXT NOT NULL,           -- always a participants row, even for an imported author who never voted
  text TEXT NOT NULL,
  source TEXT NOT NULL,              -- 'local' | 'polis'
  external_id TEXT UNIQUE,           -- Polis comment-id, so re-importing upserts
  created_at INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS votes (
  participant_id TEXT NOT NULL,
  statement_id INTEGER NOT NULL,
  vote INTEGER NOT NULL CHECK (vote IN (-1, 0, 1)),
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (participant_id, statement_id)
);
```

The latest math result is one `ctx.storage.kv` value: `"math" → MathResult`.

**RPC methods** (called by the Worker):
- `nextStatement(participantId)`
- `addStatement(participantId, text)`
- `vote(participantId, statementId, vote)`
- `importPolis({ comments, votes })`

Each write also creates a `participants` row if needed.

Unlike Polis, adding a statement doesn't record an agree vote from its author. Authors get their own statements from `nextStatement` like anyone else, so they can vote differently from how they wrote them.

**After each write:**
1. Broadcast a `counts` message.
2. Schedule the math: `if ((await storage.getAlarm()) === null) await storage.setAlarm(Date.now() + 3_000)`. This debounces bursts of votes, and an idle conversation never wakes.

**`alarm()`:**
1. Load the votes.
2. Run `computeMath`.
3. Save the result.
4. Broadcast a `math` message.

It only reads current votes and overwrites one value, so running it twice is harmless. If it throws, the alarm is retried automatically.

**Import** runs in one `ctx.storage.transactionSync`, then sets an alarm for right away.

**WebSockets** use the hibernation API:
- `ctx.acceptWebSocket(server)`, with `serializeAttachment({ participantId })` on each socket.
- A new socket immediately gets a `snapshot` message.
- Broadcasts loop over `ctx.getWebSockets()`.
- Clients never send over the socket. All writes go through HTTP.

## WebSocket messages (`src/shared/types.ts`)

```ts
type Counts = { statements: number; participants: number; votes: number };
type ServerMessage =
  | { type: "snapshot"; counts: Counts; math: MathResult | null }
  | { type: "counts"; counts: Counts }
  | { type: "math"; math: MathResult };

type MathResult = {
  computedAt: number;
  k: number | null;                 // null when too few participants to cluster
  silhouettes: Record<number, number>; // silhouette for each k tried, for debugging
  participants: { id: string; x: number; y: number; group: number | null; nVotes: number }[];
  groups: { id: number; center: [number, number]; members: number }[];
};
```

When a `counts` message shows more statements than before, and the participant has run out of statements, the page asks for `/next` again.

## Math (`src/worker/math.ts`)

This follows Polis's Clojure math (`math/src/polismath/math/`), simplified: no base clusters and no k-smoothing. It's a pure function, `computeMath(votes, statementIds) → MathResult`, so it's easy to unit-test and could later move into a Workflow or Container.

1. **Rating matrix:** participants × statements, with `null` where someone didn't vote.
2. **Fill in missing votes for PCA:** replace each `null` with that statement's average vote (`conversation.clj:352-377`).
3. **PCA:** center each column, then find the top 2 components by power iteration, 100 iterations each, with deflation between them (`pca.clj`). Uses every participant.
4. **Project each participant (sparsity-aware):**
   - Use only the statements they voted on: `(vote − center) · component`.
   - Scale by `√(statements / max(votes, 1))` (`pca.clj:134-158`), which pushes sparse voters out from the center.
5. **Choose who gets clustered** (`conversation.clj:244-269`):
   - Everyone with at least `min(7, statements)` votes.
   - If that's fewer than 15 people, add the most active voters until there are 15.
6. **Groups:**
   - Run k-means on the clustered participants' 2D points, for each k from 2 to 5.
   - Skip any k that isn't below the number of distinct points.
   - Starting centers are the first k distinct points, as in `clusters.clj:55-65`, so results are deterministic.
   - At most 100 iterations.
7. **Choose k:** the one with the highest mean silhouette score (Euclidean). No smoothing, so k may change from one recompute to the next; that's on purpose while debugging. If there are fewer than 3 distinct points, `k = null` and nobody gets a group.

## Scatter plot

- Plain SVG in React, with no chart library.
- **Every participant with at least one vote is plotted.** Those who weren't clustered (step 5) are grey with `group: null`. The rest are colored by group, and group centers are marked.
- Your own dot is highlighted by matching `participantId`.
- The page shows `k`, the silhouette for each k, and `computedAt`, to help debugging.

## CSV import (`src/worker/polis-csv.ts`)

The Worker parses the files, then calls `importPolis`. The columns come from Polis's export code (`server/src/routes/report.ts`), and headers are matched by name, not position:

- **`comments.csv`:** `timestamp, datetime, comment-id, author-id, agrees, disagrees, moderated, [importance], comment-body`
  - `comment-id` → `external_id`, `author-id` → `polis:<id>`, `comment-body` → `text`, `timestamp` (seconds) → `created_at`.
  - Each author gets a `participants` row, whether or not they voted.
  - Skip `moderated = -1` (rejected in Polis). That's the only moderation we respect.
- **`votes.csv`:** `timestamp, datetime, comment-id, voter-id, vote, [important]`
  - If a voter has several rows for one comment, the latest `timestamp` wins.
  - Skip votes on comments that weren't imported.
- **Parser:** a small RFC 4180 parser, so quoted commas, `""` and newlines inside `comment-body` work. No dependency.
- **Re-importing** the same export upserts, so nothing is duplicated.

## Tests

- **`test/math.test.ts`:**
  - Two clearly opposed voting blocs give k = 2 and the right members.
  - Participant filter thresholds, including the top-up to 15.
  - Sparse voters are pushed outward by the scaling.
  - Results are deterministic across runs.
- **`test/polis-csv.test.ts`:**
  - Quoted fields, embedded newlines, optional columns.
  - The latest vote wins; moderated-out comments are skipped.

These run under plain Vitest, since both modules are pure. DO integration tests (vote → alarm → `math` message) with `@cloudflare/vitest-pool-workers` come later, once the core works.

  - A client-side adapter from `MathResult` covers the dots, group hulls and labels: each participant becomes its own base cluster, and group members become their indices.
  - Its bar charts and "X% of group A agreed" sentence need `group-votes` (agree/disagree/saw counts per group and statement), which the alarm would compute.
  - Its statement picker needs Polis's `consensus` and `repness` math.
  - It needs a `selfId` prop (it assumes `pid === 0` is you) and a responsive width (it's fixed at 750px).
